# Changelog

All notable changes to the IPS Community Plugin will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

## [1.0.2] - 2026-04-25

### Added
- **Bypass threshold by post count.** New setting `spamtroll_bypass_min_posts`
  (ACP → Spamtroll → Settings → Bypass): members with more than N forum
  posts skip scanning entirely. Default `0` keeps the previous behaviour
  (no post-count threshold). Catches the "established member, never
  spams" case without admins manually maintaining a bypass group.
- **Polish and German translations** — full `dev/lang_pl.php` and
  `dev/lang_de.php`. The CLI installer now picks the right strings per
  language pack based on `core_sys_lang.lang_short`, so PL packs that
  previously inherited the EN default get refreshed on the next run.
  Other locales fall back to EN.

### Changed
- **Private messages are no longer scanned.** The "Posts and private
  messages" option was removed from the scan-scope dropdown; the
  Comment hook now bails out for any `\IPS\core\Messenger\*` item
  before reaching the API. The legacy `spamtroll_check_messages`
  setting is dropped from `data/settings.json` and from the database
  by the 1.0.2 upgrade handler.
- `setup/cli-install.php` now updates `core_sys_lang_words` rows
  whose `word_default` has changed (previously it only inserted
  missing rows). Custom strings that admins have overridden via ACP
  are preserved — only `word_default` plus `word_custom`-when-equal-
  to-default are refreshed.

## [1.0.1] - 2026-04-24

### Changed
- API client extracted to the shared `spamtroll/php-sdk` Composer package.
  `\IPS\spamtroll\Api\Client`, `\IPS\spamtroll\Api\Response`, and
  `\IPS\spamtroll\Api\Exception` were removed; callers now use
  `\Spamtroll\Sdk\Client`, `\Spamtroll\Sdk\Response\CheckSpamResponse`, and
  the `\Spamtroll\Sdk\Exception\*` hierarchy. Retry + score normalization
  (raw / 30) are unchanged in behavior; the only visible difference is the
  exception namespace hooks catch against.
  - New `sources/Api/IpsHttpClient.php` adapter routes SDK requests through
    `\IPS\Http\Url::external()` so IPS-level HTTP settings still apply.
  - `Application::apiClient()` now returns a `\Spamtroll\Sdk\Client`.
  - `hooks/Comment.php`, `hooks/Member.php`, and
    `modules/admin/spamtroll/settings.php::testConnection()` switched to
    the SDK's `CheckSpamRequest` / `SpamtrollException` types.
  - Install: run `composer install --no-dev` in `applications/spamtroll/`
    before packaging or before running `cli-install.php`. The installer
    now aborts early with a clear error if `vendor/autoload.php` is
    missing.

### Fixed
- Hook was attached to the wrong IPS class. `hooks/Post.php` extended `\IPS\forums\Topic\Post` and overrode `processAfterCreate()` — but `processAfterCreate()` is defined on `\IPS\Content\Item` and only runs when a **new topic** is created. Ordinary replies to existing topics never triggered it, so they were never scanned. Replaced `hooks/Post.php` and `hooks/Message.php` with a single `hooks/Comment.php` that hooks `\IPS\Content\Comment::create` (the static factory that IPS calls for every forum reply, every PM, and for the first post of each new topic via `Item::processAfterCreate` → `Comment::create`). Same pattern the CleanTalk antispam plugin uses. Verified against a live post from a real user on the forum — it appeared in `spamtroll_logs` within seconds.
- Hooks in `core_hooks` were invisible to the IPS runtime (`\IPS\IPS::$hooks` stayed empty), so posts / PMs / registrations were never intercepted — the dashboard counter stayed at zero no matter how much traffic the forum got. Root cause: IPS boots its hook cache from a single file, `plugins/hooks.php`, which is only regenerated by `\IPS\Plugin\Hook::writeDataFile()`. `setup/cli-install.php` now calls `writeDataFile()` on every run, and the file contains entries for `\IPS\forums\Topic\Post`, `\IPS\core\Messenger\Message`, and `\IPS\Member`.
- `hooks/Member.php::spamService()` signature didn't match `\IPS\_Member::spamService($type = 'register', $emailAddress = null, &$spamCode = null, &$disposable = false, &$geoBlock = false)`. IPS threw a PHP fatal the moment it tried to load the compiled hook, which happened every time any member was loaded — breaking the entire site for any flow that touches a member object. Fixed by matching the parent signature and forwarding all arguments to `parent::spamService(...)`.
- Template parse error in `logDetails.phtml`: `{{$log['log_content_preview']}}` (raw expression, no echo) changed to `{$log['log_content_preview']}` (echo). The double-brace form compiled to a bare `$log['...']` statement that broke the whole `admin/spamtroll` template group with `template_store_missing`.
- Logs table showed raw translation keys (`SPAMTROLL_LOG_LOG_ID`, `SPAMTROLL_LOG_LOG_MEMBER_ID`, …) because `$table->langPrefix = 'spamtroll_log_'` was being concatenated with column names that already started with `log_`, yielding `spamtroll_log_log_<column>`. Prefix changed to `'spamtroll_'` so `log_id` resolves to `spamtroll_log_id` (which exists in `lang.php`).
- Settings page was missing 9 language keys for the simplified `sensitivity` preset and `scan_scope` dropdown, plus 4 form section headers. Form fell back to hash placeholders. Added all of them to `dev/lang.php`.
- Dashboard "Scan Activity" box used `<canvas>` with Chart.js initialization, but IPS does not bundle Chart.js — the canvas rendered as an empty box. Replaced with a plain `ipsTable` showing total/blocked counts per day (reads `$stats['daily']` directly — no external library needed).
- Test Connection button JavaScript is now inlined into `settings.phtml`. IPS has no `addJavascript` API analogous to `\IPS\Theme::addCss()`, and the forum is not actually in Developer Mode (see note below), so there was no way to get `Output::js()` to return a URL to `dev/js/admin/spamtroll.js`. Inlining the ~30 lines of JS the button needs is simpler than standing up JS build infrastructure.
- Settings page showed the raw `<form>` HTML as escaped text because `{$form}` in the template compiles to `htmlspecialchars($form)`. Changed to `{$form|raw}` — the `|raw` filter is IPS's documented way to emit an object that already returns HTML via `__toString()`. Confirmed by searching core admin templates for the same pattern.
- Dashboard tables rendered on white `ipsTable` backgrounds that clashed with the dark ACP chrome. Replaced `ipsTable ipsTable_zebra` / `ipsTable ipsTable_responsive ipsTable_zebra` with a custom `spamtroll-table` class styled with transparent background and muted borders so it inherits whatever content-area background the ACP is using.
- Dashboard `ipsWidget` / `ipsBox` blocks (API Status, Statistics, Scan Activity, Recent Activity) had white IPS-default backgrounds. Wrapped the dashboard in `<div class="spamtroll-dashboard">` and added scoped overrides in `styles.css` that set `background: transparent` on widgets/boxes, and a subtle translucent tint on their titles — so the whole page honours the admin skin instead of punching white holes into it. The overrides need `!important` because IPS core CSS ships `.ipsBox:not(.ipsBox_transparent):not(.ipsModerated) { background: var(--c0) }` (specificity 0,0,3,0) which otherwise beats our `.spamtroll-dashboard .ipsBox` (0,0,2,0). Verified live via Playwright DOM inspection — computed `backgroundColor` is now `transparent` on every widget/box inside the dashboard.
- `cli-install.php` was compiling CSS/templates only for `\IPS\Theme::load(1)` (the default front-facing theme). The ACP reads assets from `\IPS\Theme::master()` (`_id=0`, file path `uploads/css_built_0/*`), so the ACP was served a stale pre-override CSS file even after re-running the installer. `Theme::load(0)` throws `OutOfRangeException` — you have to use `Theme::master()` for the master set. Installer now compiles for master plus every row in `core_themes`.
- Empty leading `<div class="ipsBox">` was rendered at the top of the dashboard when the app was both configured and enabled (the warning / info block inside was conditionally empty, leaving the wrapper as a ghost white rectangle). Wrapped the wrapper in the same `{{if !$isConfigured}}...{{elseif !$isEnabled}}...{{endif}}` so nothing renders when there's nothing to say.
- Stale CSS under Cloudflare: the CDN caches `/uploads/css_built_1/*.css` for `max-age=315360000` (10 years) on the plain URL. Even after fixing the nameclash by renaming the path, subsequent edits to the CSS still produce the same URL, which is already pinned in CF's cache. Admin controllers now append `?v={filemtime(dev/css/admin/spamtroll/styles.css)}` to every URL returned by `\IPS\Theme::i()->css()`, which changes whenever anyone edits the source file — Cloudflare treats it as a distinct resource and refreshes.

### Added
- `setup/cli-install.php` now imports **CSS** from `dev/css/` into `core_theme_css` and runs `\IPS\Theme::compileCss()` on every run, so `\IPS\Theme::i()->css('spamtroll.css', 'spamtroll', 'admin')` returns a URL right away. Previously CSS was ignored and the admin UI rendered unstyled.
- `setup/cli-install.php` template and CSS imports now **update-or-insert** (match by `app/location/group/name`) instead of skip-if-exists. Editing `dev/html/*.phtml` or `dev/css/*.css` and re-running the installer now picks up the changes.
- `dashboard.php`, `settings.php`, `logs.php` controllers now register their CSS/JS via `\IPS\Output::i()->cssFiles` / `jsFiles` in `execute()`.

### Changed
- CSS moved from `dev/css/admin/spamtroll.css` to `dev/css/admin/spamtroll/styles.css`. Controllers now request `\IPS\Theme::i()->css('spamtroll/styles.css', 'spamtroll', 'admin')`. Motivation: Cloudflare in front of the forum caches asset URLs for `max-age=315360000` (10 years), so editing the old CSS and recompiling left the old URL pinned to the old content. The rename produces a new built-file hash (since IPS derives the path from `app,location,path`) which sidesteps the stale CDN copy.

### Added
- **Scan UUID column in the logs list.** Every entry now carries `log_submission_id` — the UUID returned by the Spamtroll `/scan/check` endpoint — with a copy-to-clipboard button next to a truncated (`abcd1234…`) display. Clicking the button copies the full UUID and briefly flashes "Copied". Same badge also shown in the log-detail modal. Useful for correlating an IPS log entry with a scan in the Spamtroll backend.
  - `sources/Api/Response::getSubmissionId()` reads `submission_id` out of the unwrapped `scanData` payload.
  - `Application::log()` gained an optional `?string $submissionId` parameter.
  - `data/schema.json` + `setup/install.php` added the `log_submission_id VARCHAR(36)` column. Install script auto-runs `ALTER TABLE … ADD COLUMN` on forums installed before the column existed, so no manual migration is needed.
  - `modules/admin/spamtroll/logs.php` registers the column and a parser that emits the UUID badge; an inline delegated-click handler is appended to the page output for the copy behaviour (IPS has no `addJavascript` equivalent on the admin side, and the forum in question is not in real dev mode).
  - `hooks/Comment.php` and `hooks/Member.php` pass `$response->getSubmissionId()` into `log()`.
- `setup/cli-install.php` — idempotent CLI installer that registers the app and imports language strings + templates (steps IPS does NOT do automatically when an application folder is simply dropped into `applications/` with `IN_DEV=1`). Replaces the inline installation snippet that used to live in `README.md` and covered only `core_applications`/`core_modules`/`core_sys_conf_settings`.
- `setup/cli-uninstall.php` — full CLI uninstaller that clears every DB row created by the app (applications, modules, hooks, tasks, widgets, settings, language words, theme templates) and drops `spamtroll_logs`.
